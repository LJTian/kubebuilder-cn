Helm 插件（helm/v1-alpha）

helm/v2-alpha 插件根据项目的 kustomize 输出生成 Helm Chart，让你可以将 operator 以 bundle 或 Helm Chart 形式分发。

该插件根据 make build-installer 输出动态构建 Chart，并保留你的自定义内容，如环境变量、标签、注解和安全上下文。

为何使用 Helm

默认情况下，Kubebuilder 会创建一份清单 bundle：

make build-installer IMG=<registry>/<project-name:tag>

用户通过以下方式安装：

kubectl apply -f https://raw.githubusercontent.com/<org>/project-v4/<tag-or-branch>/dist/install.yaml

许多用户更偏好用 Helm 进行打包与升级。该插件将 dist/install.yaml 转换为镜像你项目的 Helm Chart。

Features

  • 根据 kustomize 输出生成 Chart，而非样板代码
  • 保留环境变量、标签、注解和补丁
  • 按 config/ 目录布局组织模板
  • 仅在 values.yaml 中包含可配置参数
  • 永不覆盖 Chart.yaml；除非使用 --force，否则保留 values.yaml、NOTES.txt、_helpers.tpl、.helmignore、test-chart.yml、network-policy/allow-metrics-traffic.yaml 和 network-policy/allow-webhook-traffic.yaml
  • 当 kustomize 输出未提供时，添加默认的 ServiceMonitor 和 NetworkPolicy 模板
  • 将自定义资源放在带有 Helm 模板的 templates/extras/ 中

Usage

基本工作流

创建项目并构建安装器捆绑包：

kubebuilder init
make build-installer IMG=<registry>/<project:tag>

从 kustomize 输出生成 Helm Chart：

kubebuilder edit --plugins=helm/v2-alpha

要重新生成被保留的文件（Chart.yaml 除外），请使用 --force：

kubebuilder edit --plugins=helm/v2-alpha --force

高级选项

使用自定义清单文件：

kubebuilder edit --plugins=helm/v2-alpha --manifests=manifests/custom-install.yaml

将 Chart 写入自定义输出目录：

kubebuilder edit --plugins=helm/v2-alpha --output-dir=charts

组合自定义清单与输出目录：

kubebuilder edit --plugins=helm/v2-alpha \
  --manifests=manifests/install.yaml \
  --output-dir=helm-charts

What is templates/extras/

标准资源（RBAC、manager、webhook、CRD）使用专用模板目录。其他资源放入 templates/extras/。

不会包含来自 config/samples/ 的自定义资源实例。即使你将 CR 实例加入 kustomize 输出，插件也会忽略它们。

Why CRDs are in templates/

尽管 Helm 最佳实践 建议将 CRD 放在顶层 crds/ 目录下，但 Kubebuilder Helm 插件有意将它们放在 templates/crd 下。

理由与 Helm 自身处理 CRD 的方式有关。默认情况下，Helm 会在首次发布时安装一次 CRD，但在后续升级时会忽略 CRD 变更。

这可能导致令人惊讶的行为：Chart 升级会静默跳过 CRD 更新，使集群不同步。

为避免认可这种行为，Kubebuilder 插件采用将 CRD 打包在 templates/ 内的方式。在此模式下，Helm 会像对待其他资源一样对待 CRD，确保它们按预期被应用和升级。虽然这会阻止在单个 Chart 中混合同类型的 CRD 与 CR（因为 Helm 无法在创建步骤之间等待），但它确保了对 CRD 可预测且明确的生命周期管理。

简而言之：

  • Helm crds/ 目录：仅一次性安装，不升级。
  • Kubebuilder templates/crd：CRD 像其他清单一样管理，包含升级。

该设计选择优先考虑正确性与可维护性，而非 Helm 的默认约定，同时为未来改进留出空间（例如为 API 和控制器分别脚手架生成独立 Chart）。

Values 配置

生成的 values.yaml 提供从实际部署中提取的配置选项。命名空间创建不由 Chart 管理；安装时请使用 Helm 的 --namespace 和 --create-namespace 标志。

values 如何格式化

在以下情况取消 values 注释：

  • 从 kustomize 源清单提取
  • 标准 Helm 字段（replicas、image、资源名称）

在以下情况 values 保持注释：

  • 未使用的可选 Kubernetes 功能（imagePullSecrets、priorityClassName）
  • 基础用法不需要的高级配置（topology spread、pod disruption budget）
  • 用户自定义字段（名称覆盖、自定义标签）

安装

该插件会向你的 Makefile 添加 Helm 目标：

make helm-deploy IMG=<registry>/<project:tag>
make helm-status

手动安装并启用全部功能：

$ helm install my-release ./dist/chart --namespace my-project-system --create-namespace

对于没有转换 Webhook 的 Chart，可通过将以下所有 values 设为 false 来禁用 Manager 及所有可选组件：

$ helm install my-release ./dist/chart \
  --set manager.enabled=false \
  --set metrics.enabled=false \
  --set webhook.enabled=false \
  --set prometheus.enabled=false \
  --set certManager.enabled=false \
  --set networkPolicy.enabled=false

对于没有转换 Webhook 的 Chart，可在不启用 Webhook 的情况下安装：

$ helm install my-release ./dist/chart --set webhook.enabled=false --set certManager.enabled=false

webhook.enabled=false 会跳过 webhook Service、webhook 配置、webhook NetworkPolicy 以及 webhook-server 容器端口。还会设置 --webhook-port=-1 以禁用 Webhook 服务器。这与 metrics.enabled=false（传入 --metrics-bind-address=0）类似。

Requires controller-runtime v0.25.0 or later

较旧的 controller-runtime 发行版会将 --webhook-port=-1 视为默认值 9443。随后 Manager 会在没有证书的情况下尝试启动 Webhook 服务器并失败。参见禁用 Webhook 服务器。

带有 CR 版本转换的 Chart 会拒绝 webhook.enabled=false。API 服务器需要 Webhook Service 来转换自定义资源。

安装并包含 NetworkPolicy 资源：

$ helm install my-release ./dist/chart --set networkPolicy.enabled=true

额外卷

向 Manager 部署添加 Webhook 与 metrics 证书之外的卷和卷挂载。

kustomize 配置（config/manager/manager.yaml 或补丁）中的卷会写入 Chart 模板。当 Manager 有额外卷时，values.yaml 会包含 manager.extraVolumes 和 manager.extraVolumeMounts 字段。可用它们在安装时添加更多卷。

Webhook 与 metrics 证书（webhook-certs、metrics-certs）单独管理，由 certManager.enabled 以及（针对 metrics TLS）metrics.enabled + metrics.secure 控制。

指标配置

metrics.port

设置 metrics.port 可更改 metrics 端点使用的端口。Chart 会将该值同时应用于 Manager 的 --metrics-bind-address 参数、metrics Service 的 port 与 targetPort，以及 metrics NetworkPolicy。

例如，将 Chart 安装为在端口 8444 上提供 metrics 端点：

helm install my-operator ./dist/chart --set metrics.port=8444

默认值为 8443，从项目配置中检测得出。

metrics.secure

控制 metrics 端点的传输安全与身份认证（默认：true）。

当为 true 时：

  • 使用带 TLS 证书的 HTTPS（当 certManager.enabled=true 时）
  • 创建用于身份认证的 metrics-auth-role ClusterRole
  • ServiceMonitor 使用 HTTPS

当为 false 时：

  • 使用无认证的 HTTP
  • 无 TLS 证书
  • ServiceMonitor 使用 HTTP

Metrics roles are always cluster-scoped

即使 rbac.namespaced=true，metrics-auth-role 和 metrics-reader 也始终是 ClusterRole。Metrics 身份认证使用集群作用域 API 来认证像 Prometheus 这样的抓取器。

Webhook 端口配置

设置 webhook.port 可更改 Manager 参数、容器端口、Service target port 和 NetworkPolicy。Service 对外暴露的端口保持不变（默认清单中为 443）。

例如，将 Chart 安装为在端口 9444 上运行 Webhook 服务器：

helm install my-operator ./dist/chart --set webhook.port=9444

默认值为 9443，从项目配置中检测得出。要禁用 Webhook 服务器，请设置 webhook.enabled=false，而不是更改端口。

健康探针端口配置

设置 manager.healthProbe.port 可更改 Manager 提供健康探针的端口。存活（/healthz）与就绪（/readyz）端点绑定到该端口。Chart 会将该值同时应用于 --health-probe-bind-address 参数、health 容器端口，以及两个探针的 httpGet 端口。

例如，将 Chart 安装为在端口 8082 上提供健康探针：

helm install my-operator ./dist/chart --set manager.healthProbe.port=8082

默认值为 8081，从项目配置中检测得出。

为 manager 传递参数

在 values.yaml 中使用 manager.args，向 Chart 未作为独立 values 暴露的 Manager 容器传递额外标志。Chart 通过 Helm 的 tpl 函数渲染每个条目，并对照 Chart 的根上下文求值，因此参数可以引用其他 values、release 信息或 Chart 模板函数，而不仅是静态字符串。

例如，从 release 命名空间设置 leader election 命名空间，并添加一个普通标志：

manager:
  args:
  - --leader-election-namespace={{ .Release.Namespace }}
  - --leader-elect

Helm 在渲染时求值 {{ .Release.Namespace }}，因此 Manager 容器会收到 --leader-election-namespace=<release-namespace>。--leader-elect 标志没有模板语法，因此会原样渲染。

Do not set the metrics, webhook, or health probe flags in manager.args

Chart 已将 --metrics-bind-address、--webhook-port 和 --health-probe-bind-address 分别暴露为 metrics.port、webhook.port 和 manager.healthProbe.port。请设置这些 values，而不是把标志加入 manager.args。插件在生成 Chart 时会从提取的参数中移除这些标志，因此无论是否模板化，通过 manager.args 再加回去都会与由 values 驱动的标志重复。Service、NetworkPolicy 和探针仍使用已配置的端口，导致流量与探针指向错误端口。

NetworkPolicy 配置

设置 networkPolicy.enabled: true 可为 Manager Pod 安装 NetworkPolicy 资源。

当 kustomize 输出包含 NetworkPolicy 资源时，插件会转换并启用它们。否则，它会生成默认的 metrics 策略，并在检测到 admission 或 CRD 转换 Webhook 时生成默认的 webhook 策略。

除非传入 --force，否则插件会保留默认 NetworkPolicy 模板。来自 kustomize 输出的策略总会重新生成，因此请在 config/network-policy/ 中编辑它们。

仅当 networkPolicy.enabled 与 metrics.enabled 均为 true 时，才会渲染生成的 metrics 策略。仅当 networkPolicy.enabled 与 webhook.enabled 均为 true 时，才会渲染生成的 webhook 策略。

metrics 策略仅允许来自带有 metrics: enabled 标签的命名空间中的 Pod 的入站流量。请为应抓取 metrics 的每个命名空间打标签：

$ kubectl label namespace <namespace> metrics=enabled

默认 webhook 策略允许所有来源访问 Manager Pod 的 webhook 端口。API 服务器通过 webhook Service 到达该端口，用于 admission 与 CRD 转换 Webhook。若要按命名空间限制 admission 请求，请在 MutatingWebhookConfiguration 或 ValidatingWebhookConfiguration 上设置 namespaceSelector。该设置控制哪些请求会调用 admission Webhook；它不会限制 NetworkPolicy 流量。

自定义标签与注解

使用 manager.labels、manager.annotations、manager.pod.labels 和 manager.pod.annotations 添加自定义标签与注解。来自 kustomize 的重复键会自动过滤。

ServiceAccount 与 ServiceMonitor 资源通过 serviceAccount.labels、serviceAccount.annotations、prometheus.labels 和 prometheus.annotations 支持相同模式。

ServiceAccount 配置

设置 serviceAccount.enabled: true（默认）以创建 ServiceAccount。设置 serviceAccount.enabled: false 以使用已有账户：

serviceAccount:
  enabled: false
  name: my-existing-sa

Chart 默认启用该开关：

serviceAccount:
  enabled: true

Helm 会将该默认值合并到省略该节的任何 values 文件中，因此省略它仍会创建账户。

当 serviceAccount.enabled: false 时，serviceAccount.name 为必填，未设置时 Chart 渲染会失败。显式设置 name: default 以使用命名空间默认 ServiceAccount。

解析后的名称会一致地用于 Deployment 以及所有 RBAC 绑定，适用于集群作用域与命名空间作用域的 RBAC 模式：

serviceAccount.enabledserviceAccount.name已创建 ServiceAccount使用的名称（Deployment + RBAC 绑定）
true (default)anyYes生成的（<fullname>-controller-manager，name 被忽略）
falsesetNo所提供的名称
falsedefaultNo命名空间默认 ServiceAccount
falseunsetNo渲染失败并给出明确错误

生成的名称由 Chart fullname 构建，通常为 <release>-<chart>，再加上 -controller-manager 后缀，并截断到 Kubernetes 的 63 字符限制。它会尊重 nameOverride 与 fullnameOverride。

Why an explicit name is required

若静默回退到命名空间默认 ServiceAccount，会将 operator 的 RBAC 权限绑定到共享身份。要求设置 serviceAccount.name 可使该选择显式化，并在渲染时捕获错误配置。

为云提供商集成添加注解：

serviceAccount:
  enabled: true
  annotations:
    iam.gke.io/gcp-service-account: my-operator@project.iam.gserviceaccount.com

外部 ServiceAccount 名称按原样使用，并忽略 nameOverride 或 fullnameOverride。

RBAC 配置

rbac.namespaced

设置 RBAC 权限作用域：

  • false（默认）：针对所有命名空间的 ClusterRole 与 ClusterRoleBinding
  • true：仅针对 release 命名空间的 Role 与 RoleBinding

What rbac.namespaced controls

这仅控制 RBAC 权限。要控制监视作用域，请使用 WATCH_NAMESPACE（Manager 作用域）。metrics-auth-role 始终是 ClusterRole，leader-election-role 始终是 Role。

rbac.roleNamespaces

当你的 kustomize 输出包含针对特定命名空间（非 Manager 命名空间）的 Role 与 RoleBinding 时，插件会自动检测并为它们创建 roleNamespaces 条目。

为控制器添加命名空间特定的 RBAC 标记：

// +kubebuilder:rbac:groups=apps,namespace=infrastructure,resources=deployments,verbs=get;list;watch
// +kubebuilder:rbac:groups="",namespace=users,resources=secrets,verbs=get;list;watch

运行 make manifests 生成 RBAC 清单，然后运行该插件。生成的 values.yaml 包含：

rbac:
  namespaced: false

  ## 部署到与 Manager 命名空间不同的命名空间的 Role 的命名空间配置
  ## 键为资源名称后缀（不含项目前缀）
  ##
  roleNamespaces:
    # RBAC 资源 manager-role-infrastructure 部署到命名空间 infrastructure
    "manager-role-infrastructure": "infrastructure"
    # RBAC 资源 manager-rolebinding-infrastructure 部署到命名空间 infrastructure
    "manager-rolebinding-infrastructure": "infrastructure"
    # RBAC 资源 manager-role-users 部署到命名空间 users
    "manager-role-users": "users"
    # RBAC 资源 manager-rolebinding-users 部署到命名空间 users
    "manager-rolebinding-users": "users"

  helpers:
    enabled: false

使用 values 文件在部署时覆盖命名空间：

# custom-values.yaml
rbac:
  roleNamespaces:
    "manager-role-infrastructure": "prod-infra"
    "manager-rolebinding-infrastructure": "prod-infra"
    "manager-role-users": "prod-users"
    "manager-rolebinding-users": "prod-users"

使用自定义命名空间安装：

helm install my-operator ./dist/chart -f custom-values.yaml

或使用 --set：

helm install my-operator ./dist/chart \
  --set 'rbac.roleNamespaces[manager-role-infrastructure]=prod-infra' \
  --set 'rbac.roleNamespaces[manager-role-users]=prod-users'

Helper roles and optional values

设置 rbac.helpers.enabled: true 可为自定义资源创建 admin、editor 和 viewer 角色。

values.yaml 中的可选字段使用 Helm 条件。注释掉它们即可从已部署清单中排除。
