Webhook 引导问题

问题所在

当你为核心 Kubernetes 类型（Pod、Deployment、Job 等）创建 webhook 时，该 webhook 可能阻塞其自身 controller Pod 的启动，导致部署死锁。

示例命令：

kubebuilder create webhook --group core --version v1 --kind Pod --programmatic-validation

示例场景：

  1. 你为 Pod 创建校验 Webhook
  2. 你部署控制器（以 Pod 运行）
  3. Kubernetes 尝试创建你的控制器 Pod
  4. 你的 Webhook 会拦截此次 Pod 创建
  5. Webhook 服务器尚未就绪（它位于正在创建的 Pod 内）
  6. Pod 创建会挂起，等待 Webhook 校验
  7. 由于 Pod 被阻塞，Webhook 永远无法启动

结果： 死锁。你的部署失败。

这种情况何时发生？

核心 Kubernetes 类型

为内置 Kubernetes 资源创建 Webhook 时会出现引导问题：

  • core group: Pod, Service, Namespace, ConfigMap, Secret
  • apps group: Deployment, StatefulSet, DaemonSet, ReplicaSet
  • batch group: Job, CronJob
  • 其他内置类型

为什么？ 你的 webhook 验证的资源类型，正是 controller 部署所创建的类型（通常是 Pod 或 Deployment）。

自定义 CRD

自定义资源 Webhook 不会出现引导问题：

  • 你的 Webhook 校验 MyResource 对象
  • 你的控制器以 Pod 运行
  • Pod 与 MyResource 是不同类型
  • 无循环依赖

如何修复

使用 namespaceSelector 或 objectSelector 配置 Webhook 跳过校验自身资源。

选项 1：namespaceSelector (recommended)

排除你的 Webhook 运行所在的整个命名空间。

步骤 1： 在 config/manager/manager.yaml 中为 Namespace 添加标签：

apiVersion: v1
kind: Namespace
metadata:
  labels:
    控制平面: 控制器管理器
    app.kubernetes.io/name: my-project
    app.kubernetes.io/managed-by: kustomize
    webhook-excluded: "true"
  name: system

步骤 2： 创建补丁文件 config/webhook/namespaceselector_patch.yaml：

# For mutating webhooks (--defaulting)
- op: add
  path: /webhooks/0/namespaceSelector
  value:
    匹配表达式:
    - key: webhook-excluded
      操作员: DoesNotExist

对于 validating webhook（--programmatic-validation），创建类似补丁并指向 ValidatingWebhookConfiguration。

步骤 3： 将补丁添加到 config/webhook/kustomization.yaml：

resources:
- manifests.yaml
- service.yaml

贴片:
- path: namespaceselector_patch.yaml
  目标:
    group: admissionregistration.k8s.io
    version: v1
    kind: 变更Webhook配置
    name: mutating-webhook-configuration

步骤 4： 部署：

make deploy IMG=<your-image>

选项 2：objectSelector

将带特定标签的 Pod 排除在 Webhook 校验之外。

步骤 1： 在 config/manager/manager.yaml 中为 Pod 添加标签：

spec:
  template:
    metadata:
      annotations:
        kubectl.kubernetes.io/default-container: manager
      labels:
        控制平面: 控制器管理器
        app.kubernetes.io/name: my-project
        webhook-excluded: "true"

步骤 2-4： 与选项 1 相同，但在补丁文件中使用 objectSelector 而非 namespaceSelector。

多个 Webhook

如果为多个核心类型（例如 Pod 和 Deployment）创建了 Webhook，你会有多个 Webhook 条目。

检查 Webhook 数量：

make manifests
grep "  name: m" config/webhook/manifests.yaml  # Count mutating webhooks
grep "  name: v" config/webhook/manifests.yaml  # Count validating webhooks

示例输出：

  name: mpod-v1.kb.io         # Index 0
  name: mdeployment-v1.kb.io  # Index 1

在补丁文件中为所有索引添加补丁：

- op: add
  path: /webhooks/0/namespaceSelector
  value:
    匹配表达式:
    - key: webhook-excluded
      操作员: DoesNotExist
- op: add
  path: /webhooks/1/namespaceSelector
  value:
    匹配表达式:
    - key: webhook-excluded
      操作员: DoesNotExist

混合 Webhook（CRD + 核心类型）

如果你同时有自定义 CRD Webhook 和核心类型 Webhook：

  • CRD Webhook 在配置中首先出现
  • 核心类型 Webhook 出现在之后
  • 统计全部 Webhook，并为你的核心类型 Webhook 索引添加补丁

示例： 若有 1 个 CRD Webhook（索引 0）和 1 个核心类型 Webhook（索引 1），补丁应针对索引 1：

- op: add
  path: /webhooks/1/namespaceSelector
  value:
    匹配表达式:
    - key: webhook-excluded
      操作员: DoesNotExist

在 namespaceSelector 与 objectSelector 之间选择

FeaturenamespaceSelectorobjectSelector
Excludes整个命名空间特定 Pod
ScopeBroadFine-grained
最适合专用 Webhook 命名空间共享命名空间
ComplexitySimple更有针对性

建议： 除非需要细粒度控制，否则使用 namespaceSelector。
