手动迁移流程

请确保你已按照安装指南安装所需组件，并且所需版本的 Kubebuilder CLI 已位于你的 PATH 中。

本指南概述了将现有 Kubebuilder 项目迁移到较新版本 Kubebuilder 框架的手动步骤。此过程包括重新搭建项目脚手架，并手动移植你的自定义代码和配置。

从 Kubebuilder v3.0.0 起，Kubebuilder 使用的所有输入都会记录在 PROJECT 文件中。请检查当前项目中的该文件，以核对已记录的配置和元数据。请参阅 PROJECT 文件文档 以更好地理解。

另外，在开始之前，建议查阅基础项目包含什么？，以便更好地理解项目布局和结构。

About Manual Migration

手动迁移比自动化方法更复杂，但能让你拥有完全控制权。在以下情况下使用手动迁移：

  • 你的项目有大量自定义内容
  • 你的版本尚无可用的自动化工具

两阶段方法（推荐用于旧布局）：

  1. 重组布局 - 将文件移到新结构（controllers → internal/controller，webhooks → internal/webhook，main.go → cmd），更新导入，测试，提交
  2. 迁移到最新版本 - 用最新版本重新搭建脚手架，移植代码

这样可以让项目在每一步都保持可用，并简化移植。提供了 AI 迁移助手来自动化重复任务。参见AI 迁移助手，其中包含可自动化两个阶段的 AI 说明。

关于后续更新： 迁移完成后，可使用 AutoUpdate 插件 或 alpha update 命令，通过三方合并自动更新脚手架，同时保留自定义内容。

阶段 1：Reorganize to New Layout (Required only for Legacy Layouts)

仅在以下任一条件为真时需要：

  • 控制器不在 internal/controller/ 中
  • Webhook 不在 internal/webhook/ 中
  • main 不在 cmd/ 中

如果你的项目已使用 internal/controller/、internal/webhook/ 和 cmd/main.go，可跳过此阶段。

1.1 创建重组分支

git checkout -b reorganize

1.2 重组文件位置

Skip if Using AI Migration Helper

如果你已使用 步骤 1：重组到新布局 AI 迁移助手，项目已完成重组。请跳到阶段 2。

将文件移到新布局：

# If you have controllers/ directory
mkdir -p internal/controller
mv controllers/* internal/controller/
rmdir controllers

# OR if you have pkg/controllers/ directory
mkdir -p internal/controller
mv pkg/controllers/* internal/controller/

# If you have webhooks in api/v1/ or apis/v1/
mkdir -p internal/webhook/v1
mv api/v1/*_webhook* internal/webhook/v1/ 2>/dev/null || mv apis/v1/*_webhook* internal/webhook/v1/ 2>/dev/null || echo "未找到可移动的 webhook 文件（如果项目没有 webhook，这是预期行为）"

# If main.go is in root
mkdir -p cmd
mv main.go cmd/

1.3 更新 package 声明

移动文件后，更新 package 声明：

控制器： 在所有 *_controller.go 和 *_controller_test.go 文件中，将 package controllers → package controller。

Webhook： 保持版本作为包名（例如，在 internal/webhook/v1/ 中 package v1 仍为 package v1）。

1.4 更新 import 路径

查找并更新所有 import：

grep -r "pkg/controllers\|/controllers\"" --include="*.go"

在找到的每个文件中更新：

  • 导入：<module>/controllers 或 <module>/pkg/controllers → <module>/internal/controller
  • 引用：controllers.TypeName → controller.TypeName

1.5 更新 Dockerfile（如需要）

如果你的 Dockerfile 对已移动路径有显式 COPY 语句，请更新它们以反映新结构，或简化为 COPY . . 并使用 .dockerignore 排除不需要的文件。

1.6 验证并提交

构建并测试重组后的项目：

make generate manifests
make build && make test

如果成功，提交布局更改。你的项目现在使用新布局。继续进入阶段 2。

阶段 2：Migrate to Latest Version

步骤 1：Prepare Your Current Project

1.1 创建迁移分支

从当前代码库创建分支：

git checkout -b migration

1.2 创建备份

mkdir ../migration-backup
cp -r . ../migration-backup/

1.3 清理项目目录

删除除 .git 外的所有文件：

find . -not -path './.git*' -not -name '.' -not -name '..' -delete

步骤 2：Initialize the New Project

关于 PROJECT 文件： 从 v3.0.0+ 起，PROJECT 文件跟踪所有脚手架元数据。如果你有该文件且所有资源都通过 CLI 创建，请先尝试 kubebuilder alpha generate。否则，按下面的手动步骤识别并重新搭建所有资源的脚手架。

2.1 识别你的 module 与 domain

从备份中识别初始化所需的信息。

Skip if Using AI Migration Helper

如果你已使用 步骤 2：发现 CLI 命令 AI 迁移助手，你已有包含所有命令的完整脚本。执行它并跳到步骤 4：移植自定义代码。

Module 路径 - 检查备份中的 go.mod 文件：

cat ../migration-backup/go.mod

查找 module 行：

module tutorial.kubebuilder.io/migration-project

Domain - 检查备份的 PROJECT 文件：

cat ../migration-backup/PROJECT

查找 domain 行：

domain: tutorial.kubebuilder.io

如果你没有 PROJECT 文件（版本 < v3.0.0），请检查 config/crd/bases/ 下的 CRD 文件，或查看 API group 名称。domain 是 API group 中 group 名称之后的部分。

2.2 初始化 Go module

使用原项目中相同的 module 路径初始化新的 Go module：

go mod init tutorial.kubebuilder.io/migration-project

将 tutorial.kubebuilder.io/migration-project 替换为你的实际 module 路径。

2.3 初始化 Kubebuilder 项目

使用 Kubebuilder 初始化项目：

kubebuilder init --domain tutorial.kubebuilder.io --repo tutorial.kubebuilder.io/migration-project

替换为你的实际 domain 和 repository（module 路径）。

Understanding init options

  • --domain：API group 的域名（例如 tutorial.kubebuilder.io）。完整 API group 为 <group>.<domain>。
  • --repo：你的 Go module 路径（与 go.mod 中相同）

2.4 启用多 group 支持（如需要）

多 group 项目将 API 组织到不同的 group 中，每个 group 位于自己的目录。当你有用于不同目的或领域的 API 时，这很有用。

通过检查备份的目录结构，确认项目是否使用多 group 布局：

  • 单 group 布局： 所有 API 在一个 group 中

    • api/v1/cronjob_types.go
    • api/v1/job_types.go
    • api/v2/cronjob_types.go

  • 多 group 布局： API 按 group 组织

    • api/batch/v1/cronjob_types.go
    • api/crew/v1/captain_types.go
    • api/sea/v1/ship_types.go

你也可以在备份的 PROJECT 文件中检查是否有 multigroup: true。

如果你的项目使用多 group 布局，请在创建 API 之前启用它：

kubebuilder edit --multigroup=true

Important

必须在创建任何 API 之前完成此操作，以确保它们按多 group 结构搭建脚手架。

按本指南操作时，你会自动获得新布局，因为你是用最新版本创建全新项目，并将代码移植进去。

步骤 3：Re-scaffold APIs and Controllers

对原项目中的每个 API 资源，在新项目中重新搭建脚手架。

3.1 识别你的全部 API

查看备份项目（../migration-backup/）以识别所有 API。无论是否有 PROJECT 文件，都建议检查备份目录，因为并非所有资源都可能通过 CLI 创建。

检查备份中的目录结构，确保不会遗漏任何手动创建的资源：

  • 在 api/ 目录（或较旧 Kubebuilder 版本生成的项目中的 apis/）中查找 *_types.go 文件：

    • 单 group：api/v1/cronjob_types.go - 提取：version v1，kind CronJob，group 来自导入
    • 多 group：api/batch/v1/cronjob_types.go - 提取：group batch，version v1，kind CronJob

  • 在这些位置检查控制器：

    • 当前： internal/controller/cronjob_controller.go 或 internal/controller/<group>/cronjob_controller.go
    • 旧版： controllers/cronjob_controller.go 或 pkg/controllers/cronjob_controller.go

如果你从 Kubebuilder v3.0.0+ 起使用 CLI 创建了所有 API，它们应出现在 PROJECT 文件的 resources 部分，例如：

resources:
  - api:
      crdVersion: v1
      namespaced: true
    controller: true
    group: batch
    kind: CronJob
    version: v1

Tip

列出所有 API 及其 group、version、kind，以及是否有控制器。这将帮助你系统地重新搭建所有脚手架。

3.2 创建每个 API 和控制器

对步骤 3.1 中识别的每个 API，重新搭建脚手架：

kubebuilder create api --group batch --version v1 --kind CronJob

出现提示时：

  • 对 “Create Resource [y/n]” 回答 yes 以生成 API 类型
  • 如果你的原项目对此 API 有控制器，对 “Create Controller [y/n]” 回答 yes

创建每个 API 后，更新生成的清单和代码：

make manifests  # Generate CRD, RBAC, and other config files
make generate   # Generate code (e.g., DeepCopy methods)

然后验证一切可以编译：

make build

这些步骤确保新搭建的 API 正确集成。有关 API 创建工作流的详细演练，请参见快速开始指南。

对项目中的所有 API 重复此过程。

Using External Types (controllers for types not defined in your project)

如果你的项目有针对 Kubernetes 内置类型（如 Deployment、Pod）或其他项目类型的控制器：

kubebuilder create api --group apps --version v1 --kind Deployment --resource=false --controller=true

或者针对其他项目的 CRD，例如 cert-manager 的 Certificate 类型：

kubebuilder create api --group "cert-manager" --version v1 --kind Certificate --controller=true --resource=false --make=false --external-api-path=github.com/cert-manager/cert-manager/pkg/apis/certmanager/v1 --external-api-domain=io --external-api-module=github.com/cert-manager/cert-manager@v1.18.2

使用 --resource=false 跳过创建 API 定义，仅搭建控制器脚手架。

请确保查看使用外部类型以获取更多详细信息。

创建所有资源后，重新生成清单：

make manifests
make generate

3.3 重新脚手架生成 Webhook（如适用）

如果原项目有 webhook，你需要重新搭建它们的脚手架。

识别备份项目中的 Webhook：

  1. 从目录结构查找 webhook 文件：

    • 旧位置（v3 及更早）：api/v1/<kind>_webhook.go 或 api/<group>/<version>/<kind>_webhook.go
    • 当前位置（单 group）：internal/webhook/<version>/<kind>_webhook.go
    • 当前位置（多 group）：internal/webhook/<group>/<version>/<kind>_webhook.go

  2. 从 PROJECT 文件（如可用）检查每个资源的 webhooks 部分：

resources:
  - api:
      ...
    webhooks:
      defaulting: true
      validation: true
      webhookVersion: v1

重新脚手架生成 Webhook：

对每个带有 Webhook 的资源运行：

kubebuilder create webhook --group batch --version v1 --kind CronJob --defaulting --programmatic-validation

Webhook 选项：

  • --defaulting - 创建默认值 Webhook（设置默认值）
  • --programmatic-validation - 创建校验 Webhook（校验创建/更新/删除操作）
  • --conversion - 创建转换 Webhook（用于多版本 API，见下一节）

3.4 重新脚手架生成转换 Webhook（如适用）

如果你的项目有带 conversion webhook 的多版本 API，需要设置 hub-spoke 转换模式。

Understanding Hub-Spoke Conversion

在 Kubernetes 多版本 API 中，hub 是所有其他版本（spoke）与之相互转换的版本：

  • Hub 版本：通常是最完整/稳定的版本（往往是存储版本）
  • Spoke 版本：通过 hub 进行转换的所有其他版本

hub 实现 Hub() 标记接口，而 spoke 实现 ConvertTo() 和 ConvertFrom() 方法以与 hub 相互转换。

设置转换 Webhook：

为 hub 版本创建 conversion webhook，并使用 --spoke 标志指定 spoke 版本。

注意： 下面示例中使用 v1 作为 hub 仅作说明。请选择项目中应作为中心转换点的版本——通常是功能最完整且稳定的存储版本，不一定是最旧或最新的版本。

kubebuilder create webhook --group batch --version v1 --kind CronJob --conversion --spoke v2

该命令：

  • 为作为 hub 版本的 v1 创建 conversion webhook
  • 将 v2 配置为与 hub v1 相互转换的 spoke
  • 生成带有转换方法存根的 *_conversion.go 文件

对于多个 spoke，将它们指定为逗号分隔的列表：

kubebuilder create webhook --group batch --version v1 --kind CronJob --conversion --spoke v2,v1alpha1

这将 v1 设为 hub，并将 v2 和 v1alpha1 都设为 spoke。

你需要实现的内容：

该命令会生成方法存根，你将在步骤 4 中填写：

  • Hub 版本：实现 Hub() 方法（通常只是一个标记）
  • Spoke 版本：实现带有转换逻辑的 ConvertTo(hub) 和 ConvertFrom(hub) 方法

有关实现转换逻辑的全面指导，请参见多版本教程。

Forget a type of webhook ?

如果忘记了某种 webhook 类型，使用 --force 重新运行命令：

kubebuilder create webhook --group batch --version v1 --kind CronJob --defaulting --force

Webhook for External Types

对于外部类型，你也可以创建 webhook：

kubebuilder create webhook --group apps --version v1 --kind Deployment --defaulting --programmatic-validation

更多信息：Webhook 概览、准入 Webhook 以及为外部类型创建 Webhook。

搭建所有 webhook 脚手架后，验证一切可以编译：

make manifests && make build

步骤 4：Port Your Custom Code

Using AI Migration Helper

如果你已使用 步骤 3：移植自定义代码 AI 迁移助手，代码已移植完成。

你可以跳到步骤 5。不过仍建议至少审阅以下步骤并做手动验证，确保所有代码都已正确移植。

将自定义业务逻辑和配置从备份手动移植到新项目。

Use diff tools

使用 IDE 差异工具或类似 diff -r ../migration-backup/ . 的命令比较目录，识别需要移植的所有自定义内容。大多数现代 IDE 支持目录级比较，这会使过程容易得多。

4.1 移植 API 定义

比较并合并备份项目中的自定义 API 字段和标记。

需要对比的文件：

  • 单 group： api/v1/<kind>_types.go
  • 多 group： api/<group>/<version>/<kind>_types.go

需要移植的内容：

  1. Spec 与 Status 结构体中的自定义字段
  2. 验证标记 - 例如 +kubebuilder:validation:Minimum=0、+kubebuilder:validation:Pattern=...
  3. CRD 生成标记 - 例如 +kubebuilder:printcolumn、+kubebuilder:resource:scope=Cluster
  4. 子资源（SubResources） - 例如 +kubebuilder:subresource:status、+kubebuilder:subresource:scale
  5. 文档注释 - 用于 CRD 描述

有关所有可用标记，请参见 CRD 生成、CRD 验证 和标记。

如果你的 API 引用了父包（例如 scheduling.GroupName），请移植它：

mkdir -p api/<group>/
cp ../migration-backup/apis/<group>/groupversion_info.go api/<group>/

移植 API 定义后，重新生成并验证：

make manifests  # Generate CRD manifests from your types
make generate   # Generate DeepCopy methods

这可确保在继续之前正确生成 API 类型和 CRD 清单。

4.2 移植控制器逻辑

需要对比的文件：

  • 当前单 group： internal/controller/<kind>_controller.go
  • 当前多 group： internal/controller/<group>/<kind>_controller.go

需要移植的内容：

  1. Reconcile 函数实现 - 你的核心业务逻辑
  2. 辅助函数 - 控制器文件中的任何额外函数
  3. RBAC 标记 - +kubebuilder:rbac:groups=...,resources=...,verbs=...
  4. 额外的 watch - SetupWithManager 中的自定义 watch 配置
  5. 导入 - 控制器需要的任何额外包
  6. 结构体字段 - 添加到 Reconciler 结构体的自定义字段

有关权限标记的详细信息，请参见 RBAC 标记。

移植控制器逻辑后，重新生成清单并验证编译：

make generate
make manifests
make build

4.3 移植 Webhook 实现

Webhook 在不同 Kubebuilder 版本之间位置有变化。请注意路径差异：

旧版 webhook 位置（Kubebuilder v3 及更早）：

  • api/v1/<kind>_webhook.go
  • api/<group>/<version>/<kind>_webhook.go

当前 Webhook 位置：

  • 单 group：internal/webhook/<version>/<kind>_webhook.go
  • 多 group：internal/webhook/<group>/<version>/<kind>_webhook.go

需要移植的内容：

  1. Defaulting webhook - Default() 方法实现
  2. Validation webhook - ValidateCreate()、ValidateUpdate()、ValidateDelete() 方法
  3. Conversion webhook - ConvertTo() 和 ConvertFrom() 方法（用于多版本 API）
  4. 辅助函数 - 任何验证或默认值辅助函数
  5. Webhook 标记 - 通常自动生成，但请验证它们符合你的需求

Important

即使 webhook 文件位于不同位置，实现逻辑大体相同。复制方法实现，而不是整个文件。

有关详细信息，请参见 Webhook 概览、准入 Webhook 和多版本教程。

针对转换 Webhook：

如果你有 conversion webhook，请确保在步骤 3.4 中使用了 create webhook --conversion --spoke <version> 命令。这会自动设置 hub-spoke 基础设施。你只需在 spoke 版本的 ConvertTo() 和 ConvertFrom() 方法以及 hub 版本的 Hub() 方法中填写转换逻辑。

该命令会创建所有必要的样板代码——你只需实现版本之间字段转换的业务逻辑。

移植 Webhook 后，重新生成并验证：

make generate
make manifests
make build

4.4 移植 main.go 自定义内容（如有）

文件： cmd/main.go

大多数项目不需要自定义 main.go，因为 Kubebuilder 会自动处理所有标准设置（注册 API、设置控制器和 webhook、Manager 初始化、metrics 等）。

仅移植不属于标准脚手架的自定义内容。将备份的 main.go 与新搭建的文件比较，识别你添加的任何自定义逻辑。

4.5 配置 Kustomize 清单

config/ 目录包含用于部署 operator 的 Kustomize 清单。与备份比较，确保所有配置都已正确设置。

审查并更新这些目录：

  1. config/default/kustomization.yaml - 主 kustomization 文件

    • 如果你有 webhook，确保启用了 webhook 配置（取消注释与 webhook 相关的 patches）
    • 如果使用 webhook，确保启用了 cert-manager（取消注释 certmanager 资源）
    • 根据原始配置启用或禁用 metrics 端点
    • 审查命名空间与名称前缀设置

  2. config/manager/ - 控制器 Manager 部署

    • 除非有自定义，通常无需更改。如有自定义，请将资源 limits 和 requests 与备份比较，并检查环境变量

  3. config/rbac/ - RBAC 配置

    • 通常由标记自动生成——无需手动更改
    • 仅在有标记未覆盖的自定义 role binding 或 service account 配置时检查

  4. config/webhook/ - Webhook 配置（如适用）

    • 通常自动生成 - 无需手动更改
    • 仅在有自定义 webhook service 或证书配置时检查

  5. config/samples/ - 示例 CR 清单

    • 从备份复制你的示例资源

配置 Kustomize 后，验证清单能正确构建：

make all
make build-installer

4.6 移植额外自定义内容

从备份移植任何额外的包、依赖和自定义内容：

额外包（例如 pkg/util）：

cp -r ../migration-backup/pkg/<package-name> pkg/
# 更新导入路径（适用于 macOS 和 Linux）
find pkg/ -name "*.go" -exec sed -i.bak 's|<module>/apis/|<module>/api/|g' {} \;
find pkg/ -name "*.go.bak" -delete

对于依赖，运行 go mod tidy，或对复杂项目从备份复制 go.mod/go.sum。

检查其他自定义内容（Makefile、Dockerfile、测试文件）。使用 diff 工具与备份比较，识别遗漏的文件。

Using diff tools

使用 IDE 的 diff 工具将当前目录与备份（../migration-backup/）比较，或使用 git 将当前分支与 main 分支比较。这有助于识别可能遗漏的任何文件。

移植所有自定义内容后，验证一切可以构建：

make all

步骤 5：Test and Verify

与备份比较，确保所有自定义内容都已正确移植，例如：

diff -r --brief ../migration-backup/ . | grep "Only in ../migration-backup"

运行测试并验证功能：

make test && make lint-fix

部署到测试集群（例如 kind）并验证更改（即验证预期行为、运行回归检查、确认完整 CI 流水线仍能通过，并执行 e2e 测试）。

If You Have a Helm Chart

如果你有用于分发项目的 Helm chart，可能希望用 helm/v2-alpha 插件 重新生成，然后应用你的自定义内容。

kubebuilder edit --plugins=helm/v2-alpha

将备份中的 chart/values.yaml 和自定义模板与新生成的 chart 比较，应用你的自定义内容，并确保一切仍像以前一样工作。
